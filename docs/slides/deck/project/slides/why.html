4 · Why we think it works

A frame’s finish time is predictable, so we can balance it

T =

queued + frame size

link rate

+ queueing delay + one-way delay

Split rule

Choose the split S₁ + S₂ = S so both parts finish together: T₁(S₁) = T₂(S₂). One linear equation, one answer.

Worked example

Two 1.6 Mbit/s links (one-way 15 ms and 75 ms), an 85 KB frame: one link 440 ms; split 48.5 / 36.5 KB, both done at 258 ms.

Example worked from the formula, not measured. Our 250 ms target is what makes 258 vs 440 ms matter.

Formally, T_p = (U_p + S)/R_p + (sRTT_p − minRTT_p) + minRTT_p/2: time to drain what is queued plus this frame at the link's measured rate, the extra delay the buffer adds right now, and half the minimum round trip. Setting T_1(S_1) = T_2(S − S_1) and solving gives S_1 = ((U_2 + S)/R_2 + d_2 − U_1/R_1 − d_1) / (1/R_1 + 1/R_2), clamped between 0 and S, where d_p is the two delay terms. Example: rates 200 KB/s each, d_1 = 15 ms, d_2 = 75 ms, empty queues, S = 85 KB (the largest frame in our clip, from a camera cut): S_1 = 0.485 s / 0.01 s per KB = 48.5 KB; both parts finish at 257.5 ms, versus 440 ms on one link. A packet scheduler cannot do this because it never sees the frame boundary. Risk: the rate estimate R can be wrong; reference R2 (F2 given the true rates) measures how much that costs.
